# 19 — Technical Debt Register

Status: Phase 14 complete. Classified CRITICAL/HIGH/MEDIUM/LOW. This register focuses on debt *not* already fully covered as a standalone item in [18-security-review.md](18-security-review.md) — security-classed findings are cross-referenced rather than repeated in full.

## CRITICAL

| ID | Problem | Evidence | Impact | Future treatment |
|---|---|---|---|---|
| DEBT-001 | No database transactions anywhere in the codebase | `grep -rl "trans_start\|trans_begin\|trans_commit"` returns zero hits across all modules | Every multi-table write (bid+auto-bid cascade, sale settlement, invoice creation) can leave data permanently inconsistent on partial failure | Non-negotiable for a rebuild — wrap every multi-step write in a transaction; consider an ORM/framework that makes this the default rather than opt-in |
| DEBT-002 | No row locking / optimistic concurrency anywhere | Same grep sweep; bid placement confirmed unlocked read-then-write | Race conditions on the single highest-value operation in the platform (bidding) | Rebuild with `SELECT FOR UPDATE` or an equivalent optimistic-version column as a first-class pattern |
| DEBT-003 | Three independent, duplicated REST API implementations (`getapi`/`api`/`apis`) with diverging validation, one containing an unvalidated bid-insertion method | [02](02-repository-inventory.md), [10](10-api-catalogue.md), [18](18-security-review.md) SEC-002 | Security surface no one is actively maintaining; any fix to `getapi` doesn't propagate to the other two | Decommission `api`/`apis` entirely (confirm inert first) before any rebuild; a rebuild should have exactly one API implementation |
| DEBT-004 | At least six to eight independently-coded login/credential-issuing paths | [04](04-users-and-permissions.md) §9 | Any auth fix must be applied N times or it silently misses some paths; already resulted in one (`token_update`) shipping with zero credential check | Single, centralized auth service in the rebuild — no exceptions |
| DEBT-005 | The one real DB migration is provably broken (bare `ENUM()` call, duplicate array keys) and no other schema-as-code exists | [02](02-repository-inventory.md), [11](11-database-model.md) #1 | The live schema cannot be reliably reproduced from source; any environment rebuild/staging setup depends on tribal knowledge or a DB dump | A rebuild must start from a real, versioned migration history from day one |

## HIGH

| ID | Problem | Evidence | Impact | Future treatment |
|---|---|---|---|---|
| DEBT-006 | ACL/RBAC system built but never enforced (commented out) | [04](04-users-and-permissions.md) §2, SEC-020 | Every "should only role X be able to do this" question in the codebase currently has no real answer | Either finish wiring the existing ACL design or replace it — but pick one and enforce it everywhere |
| DEBT-007 | Two structurally parallel bid-log tables (`bid`, `live_auction_bid_log`) with divergent column sets and divergent status vocabularies (`won` vs `win`) | [11](11-database-model.md) | Reports/queries filtering on one status spelling silently miss rows written with the other | Unify into one bidding-event model in the rebuild, or at minimum fix the vocabulary drift immediately in the legacy system if it must keep running |
| DEBT-008 | Whole-module duplication beyond the API layer: `auction`/`auction_____`, `users`/`user`, `customer`/`visitor` (near-byte-identical), `cars/Common_Model.php`/`admin/Common_model.php` | [02](02-repository-inventory.md), [11](11-database-model.md) #7 | Maintenance burden, confusion about which copy is "real," and (per `Common_Model`) a hardcoded encryption key using the removed `mcrypt` extension duplicated into two places | Delete confirmed-dead duplicates; consolidate the rest |
| DEBT-009 | Two parallel user tables (`users`, `users2`) with independently duplicated auth logic | [11](11-database-model.md) | A user in one table is invisible to logic hardcoded against the other — data integrity and login-consistency risk | Consolidate to one user table/model in the rebuild; audit for orphaned `users2` accounts before migration |
| DEBT-010 | Monetary values appear to be stored/computed without fixed-point precision anywhere in the model layer | [11](11-database-model.md) #4 | Rounding drift risk across bid increments, commissions, and settlement totals — cannot be ruled out without DB introspection | Confirm actual column types; standardize on integer minor-units or DECIMAL in the rebuild regardless |
| DEBT-011 | Soft-delete vs. hard-delete is inconsistent even within the same table (`transaction.delete_status` exists but is bypassed by hard-delete code elsewhere) | [11](11-database-model.md) #5 | Unpredictable data-loss behavior depending on which code path performs a "delete" | Pick one deletion strategy per entity and enforce it centrally |
| DEBT-012 | Cronjob controller has no in-app authentication and no evidence of a real OS-level scheduler in the repo | [14](14-background-jobs.md), SEC-010 | Auction-closing/reserve-resolution logic is callable by anyone who finds the URL, and its actual production cadence is undocumented | Move to a proper job scheduler (queue worker, cron with a shared secret, or managed scheduler) with no public HTTP trigger |
| DEBT-013 | Deploy/debug utility files (`deploy.php`, `test.php`) shipped unauthenticated at the web root | SEC-001, SEC-004 | Evidence of no pre-deploy checklist stripping debug artifacts — a process gap, not just two isolated bugs | Add a build/deploy step that fails if debug files are present; adopt a proper CI/CD pipeline (the presence of a Jenkinsfile in the chatbot-admin project shows the team has done this elsewhere) |
| DEBT-014 | Every third-party integration credential is hardcoded in committed source rather than environment/secrets-managed | SEC-022 | A source leak of any kind is a full credential leak across payments, SMS, push, realtime, and auth simultaneously | Move to environment variables + a secrets manager as a baseline rebuild requirement |

## MEDIUM

| ID | Problem | Evidence | Impact | Future treatment |
|---|---|---|---|---|
| DEBT-015 | EAV pattern (`item_category_fields`/`item_fields_data`) layered on top of an already-wide `item` table, with attribute placement (real column vs. EAV row) decided ad hoc per category | [11](11-database-model.md) | Harder to query/report on consistently; two different mental models for "what's an item's attribute" | A rebuild should pick one pattern — likely a cleaner structured-attributes model per category, not a hybrid |
| DEBT-016 | JSON-as-schema-escape-hatch (`invoices.other_details` dumps unmapped POST fields wholesale; bilingual text stored as JSON blobs) | [11](11-database-model.md) #8 | Schema-less data that's hard to query, index, or validate | Bilingual JSON is a defensible i18n choice if kept deliberate; `other_details`-style catch-alls should become real columns |
| DEBT-017 | `sold_items.price` denormalized from `bid.bid_amount` with no sync mechanism, compounded by DEBT-001's lack of transactions | [11](11-database-model.md) #8 | Silent data drift between the two values on any partial failure | Derive at read time, or add reconciliation tooling if denormalization is kept for performance reasons |
| DEBT-018 | Widespread typos baked into load-bearing identifiers (`total_deposite`, `item_expencses`, `sort_catagories`, `orignal_name`, `milleage`, `palceBids`, `cradit_card`) | [11](11-database-model.md) #7, [10](10-api-catalogue.md) | Cosmetic but pervasive — increases onboarding friction and copy-paste error risk (evidenced by the mixed `chahge_status`/`change_status` naming across modules) | Not worth fixing in the legacy system; a rebuild is the natural point to correct all of these |
| DEBT-019 | `payments`/`orders`/`order_items`/`adjustment_items` tables referenced but never inserted into anywhere in the reviewed codebase, alongside unrelated e-commerce vocabulary (`custom_addon`, `logo_is_approved`) | [11](11-database-model.md) | Likely leftover boilerplate from an unrelated template — dead weight, and confusing for anyone reverse-engineering the schema without this context | Confirm with the business, then remove if truly dead |
| DEBT-020 | Two calendar libraries, two mapping libraries declared in the mobile app, only one of each actually used | [07](07-mobile-app.md) | Unnecessary app size/dependency surface | Prune unused dependencies in the rebuild (or immediately in the current app if it's still being maintained) |
| DEBT-021 | Client-side "did this succeed" detection via hardcoded string-matching on response text/HTML, repeated ~8 times independently across mobile screens | [07](07-mobile-app.md) §7 | Fragile to any backend copy change; duplicated rather than centralized | Rebuild should use structured status codes/booleans, never string-matching, and centralize the check in one place |
| DEBT-022 | No named-route table / central route guard in the mobile app | [07](07-mobile-app.md) §9 | All "is this screen allowed" logic is implicit (sidebar visibility + server 401s) rather than centrally enforced | Standard for JWT+401 architectures, but worth an explicit route-guard layer in a rebuild for defense-in-depth |
