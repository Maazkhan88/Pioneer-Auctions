# 16 — Edge Case Catalogue

Status: Phase 16 complete, derived from the confirmed mechanics in [06-bidding-engine.md](06-bidding-engine.md), [05-auction-lifecycle.md](05-auction-lifecycle.md), and [11-database-model.md](11-database-model.md). "Current behaviour" reflects what the code actually does (or provably fails to do); "Expected behaviour" is a plausible real-world auction-platform expectation, not a confirmed business requirement — treat as a discussion prompt, not a spec.

| # | Scenario | Current behaviour (observed) | Expected/plausible behaviour | Risk | Recommendation focus |
|---|---|---|---|---|---|
| EC-01 | Two bidders submit a bid on the same lot within milliseconds | Both read the same "current price" via an unlocked query; both can insert successfully; no guarantee the higher amount lands with the later ID | Server serializes bid acceptance; second bid is validated against the first's committed result | HIGH — lost updates, incorrect leader shown | Add row locking/transaction/optimistic version check around bid acceptance ([06](06-bidding-engine.md) §4) |
| EC-02 | Mobile bidder and hall operator bid on the same live lot simultaneously | Both write `live_auction_bid_log` via the same unsynchronized pattern — no coordination | One authoritative path arbitrates, or hall session explicitly "locks" bidder input during operator-only windows | HIGH — same table, two uncoordinated writers | Introduce a lot-level lock/mode flag arbitrating bidder vs. operator input |
| EC-03 | Client double-taps "place bid" / network retry resends the same request | No idempotency key; likely inserts twice (only incidentally caught by the stale-price check on the *second* request if timing allows) | Duplicate submissions are deduplicated (idempotency key/nonce) | MEDIUM | Add a client-generated request ID the server can dedupe on |
| EC-04 | Bidder submits an increment below any reasonable minimum (e.g. $0.01 more) | Accepted — no server-side minimum-increment check exists | Rejected with a minimum-increment error (the UI copy for this already exists but is unwired) | HIGH | Wire the existing (currently dead) `min_increment` validation into `placebid()`/`place_bid_live()` |
| EC-05 | Two proxy (auto) bidders share the exact same `bid_limit` | No documented tie-break rule found; behaviour depends on unconfirmed query ordering of `bid_auto` rows | A documented, deterministic tie-break (e.g. earliest-created proxy bid wins) | MEDIUM — UNKNOWN, needs direct verification | Confirm actual `ORDER BY` behavior, then decide/document the intended rule |
| EC-06 | Reserve not met when an online/closed auction expires | Auto-flips to `sold_status='approval'`, seller emailed for a manual decision | Same — this is a deliberate, sensible fallback as implemented | LOW (working as designed) | Confirm the actual approval/accept action (not located in this review) is itself safe/authorized |
| EC-07 | Reserve not met when a live-hall lot is being resolved | No automatic check at all — 100% operator discretion | UNKNOWN whether this should mirror online auctions' auto-approval fallback | MEDIUM — business-dependent | Confirm with the business whether this is intentional |
| EC-08 | Staff retracts a bid or rolls back an entire auction's bids | Hard `DELETE`, no soft-delete, no audit trail of what was removed or by whom | Retraction is logged/reversible, or at minimum audited | HIGH | Convert to soft-delete + audit log before any similar action ships in a rebuild |
| EC-09 | Non-auctioneer staff account (e.g. Cashier, Marketing role) accesses the live-hall operator console | Permitted — no role-7-specific check, ACL is disabled | Only "Live Auction Controller" role (or Admin) can perform operator actions | HIGH | Re-enable/repair the ACL check with a correct permission matrix |
| EC-10 | Lot's `bid_end_time` passes while a bid request is already in-flight (server clock edge) | `place_bid_live`/`placebid` re-check status/time server-side per request, so a request that arrives after expiry should be rejected — but there's no explicit lock preventing a request that started just before expiry from completing just after, racing the cron/status-flip | A bid in flight at the exact closing instant is deterministically accepted or rejected, not timing-dependent | LOW-MEDIUM | Consider a short grace/lock window around closing transitions |
| EC-11 | `auto_sale_auction_items()` cron fails partway through resolving multiple lots | No transaction — some lots resolved, others not, with no automatic resumption/retry logic found | Idempotent, resumable job; partial failure doesn't require manual intervention to identify what's unresolved | HIGH | Wrap each lot's resolution in its own transaction; add a reconciliation report |
| EC-12 | `sold_items.price` diverges from `bid.bid_amount` due to a partial failure between the two writes | Nothing detects or corrects this — no reconciliation job found anywhere | A periodic integrity check flags/fixes divergence | MEDIUM | Add reconciliation tooling, or eliminate the denormalization by deriving price at read time |
| EC-13 | Winner refuses to pay / fails to complete payment post-win | Not directly traced in this review — `sold_items.payment_status` exists but the "what happens if it stays unpaid" workflow (re-listing? penalty? deposit forfeiture?) was not located | A defined follow-up workflow (reminder, penalty, re-list) | UNKNOWN | Needs direct business/code confirmation — flagged as an open question |
| EC-14 | Item is withdrawn/becomes unavailable mid-bidding | No explicit "withdrawn" status was confirmed among the `auction_items.sold_status` values found (`not`/`sold`/`not_sold`/`approval`/`return`) | A distinct withdrawn state, with in-flight bids handled explicitly (voided/refunded) | MEDIUM — UNKNOWN | Confirm whether withdrawal is modeled at all, or handled ad hoc |
| EC-15 | Bidder's account is deactivated (`status != 1`) while they have an active session/token | `validateToken()` re-checks live DB status on every request, so subsequent bids are correctly rejected (`USER_NOT_ACTIVE`) | Same | LOW (working as designed) | None needed |
| EC-16 | Client submits `token_update` with an arbitrary/guessed user ID | **Succeeds** — issues a valid login token for that user with zero credential check, including for Admin accounts | Request rejected without valid prior authentication | CRITICAL | This is SEC-012 — fix before anything else in this list |
| EC-17 | WebSocket/Pusher disconnect during active bidding | No reconnect/catch-up/event-replay mechanism was identified server-side; client must explicitly re-fetch current state | Automatic resync on reconnect, ideally with a "you may have missed events" indicator | MEDIUM | Add an event sequence/version the client can reconcile against on reconnect |
| EC-18 | Server restart / deploy during an active live-hall auction | Not directly evaluated (infrastructure-level); `deploy.php` triggers an unauthenticated `git pull` with no visible graceful-restart coordination | Zero-downtime deploys, or deploys blocked during an active live session | UNKNOWN | Infra-level question, flagged alongside SEC-001 |
| EC-19 | Database becomes briefly unavailable mid multi-statement sale-settlement sequence | No transaction wraps the 4-statement settlement sequence — a mid-sequence DB error leaves `bid`, `sold_items`, `item`, `auction_items` inconsistent with each other | Atomic settlement (all-or-nothing) | HIGH | Wrap settlement in a transaction (also closes EC-11/EC-12) |
| EC-20 | Admin corrects the recorded winner after the fact | `updateitembuyer()` allows this directly, with **no validation that the newly-assigned buyer ever actually bid on the item**, and no audit trail | A corrected-winner action requires justification/audit logging and ideally validates the new buyer participated | HIGH | Add validation + audit trail before this action ships in a rebuild |
| EC-21 | Two users register with the same email via different paths (e.g. one via normal registration, one via `fb_login_register` with the same asserted email) | Social-login handlers look up by email and log in/auto-register with no provider verification — a malicious actor asserting an existing user's email via social login would be logged into that existing account | Provider-verified identity prevents email-assertion account takeover | CRITICAL | This is SEC-016 |
| EC-22 | A single OTP/reset code collides between two different users (10,000 possible values, no per-user scoping on password-reset lookup) | The reset-code lookup (`WHERE reset_password_code = $code`) is not scoped by email/user — a collision could reset the wrong account's password | Reset code lookups are always scoped to the specific user who requested them | HIGH | This is part of SEC-017 |

## Cross-reference

Most HIGH/CRITICAL rows above trace directly back to a specific SEC-* finding in [18-security-review.md](18-security-review.md) — that document is the authoritative severity/remediation-priority source; this table exists to frame the same underlying issues as concrete "what happens when..." scenarios useful for writing acceptance tests against a rebuild.
